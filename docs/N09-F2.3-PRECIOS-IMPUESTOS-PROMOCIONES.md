# N09-F2.3 — Listas de precios, impuestos y promociones por ámbito

## Estado
Implementación full-stack en curso en `feat/n09-f2-3-price-lists-taxes-promotions`. Este documento fija el alcance funcional; no declara la fase implementada ni aceptada.

## Requisitos rectores
- Los precios, impuestos y promociones deben admitir alcance corporativo, entidad legal o sucursal, con asignaciones explícitas.
- No se introduce herencia ni precedencia implícita entre ámbitos mientras D0-10 no esté aprobada. Si dos configuraciones aplicables generan ambigüedad, la operación debe rechazarse con un error de configuración identificable.
- Toda operación económica identifica la sucursal y la entidad legal responsable.
- Importes y tasas se calculan con tipos decimales exactos en PostgreSQL; nunca con punto flotante.
- No se realizan conversiones monetarias ni se infiere moneda funcional a partir de la zona horaria o moneda declarada de sucursal.
- Los cambios futuros de configuración no modifican pedidos históricos.

## Listas de precios
- Una lista tiene identidad, nombre, moneda explícita, ámbito, estado y vigencia.
- Las listas pueden ser corporativas, de una entidad legal o de una sucursal.
- Sus asignaciones a sucursales y entidades legales son explícitas y se validan contra las relaciones organizacionales existentes.
- Los precios se definen por producto del catálogo maestro. Las variantes de F2.2 no adquieren precio diferencial por esta fase, salvo requisito posterior aprobado.
- La resolución de precio para un pedido debe producir exactamente una lista aplicable; cero o más de una coincidencia se informa como configuración faltante/ambigua, sin fallback silencioso.
- El pedido conserva lista, moneda, precio unitario y datos de vigencia usados al confirmar.

## Impuestos por producto
- Cada producto puede tener una configuración fiscal propia; productos distintos pueden usar conjuntos de impuestos y tasas distintos.
- Cada asignación fiscal de producto define explícitamente el modo de precio: `inclusive` (el precio ya incluye el impuesto y el sistema lo desglosa) o `exclusive` (el impuesto se calcula y se suma al precio).
- El modo inclusive/exclusive se configura por producto, no como una única regla global. Una misma organización puede operar ambos modos simultáneamente en productos distintos.
- Un producto puede tener uno o varios componentes de impuesto configurados. Cada componente conserva identidad, nombre, tasa decimal, ámbito/entidad legal aplicable, vigencia y metadatos de cálculo necesarios.
- Las tasas no se codifican en el programa ni se inventan por país. Se administran explícitamente y se validan para la entidad legal responsable.
- El motor calcula cada componente y conserva base, tasa, importe, modo y referencia de regla aplicada en el snapshot del pedido y de cada línea.
- La suma y el desglose deben reconciliar exactamente con el total cobrado. La política de redondeo debe ser explícita y consistente en persistencia y backend; no usar floats.
- La configuración debe impedir reglas fiscales incompatibles o ambiguas para un mismo producto, entidad legal y fecha.
- La antigua configuración global `settings.tax_rate` no puede seguir afectando nuevos pedidos después de activar F2.3. Los históricos no se recalculan ni se reescriben.

## Promociones
- Una promoción puede ser corporativa dirigida explícitamente a una o varias sucursales, o local de una sucursal.
- Toda promoción declara vigencia, estado, alcance, elegibilidad, productos/categorías objetivo y parámetros de descuento.
- El backend valida y calcula las promociones en la transacción de creación/confirmación del pedido; nunca confía en descuentos enviados por el cliente.
- El pedido conserva el identificador y snapshot inmutable de cada promoción aplicada, base de cálculo, descuento y líneas afectadas.
- La compatibilidad, acumulación, prioridad y exclusividad se modelan explícitamente; no se aplica stacking implícito ni se permite que el orden de lectura altere el resultado.
- Una promoción inválida, vencida, fuera de alcance o no elegible no se aplica.

## Pedidos e inmutabilidad
- El precio, descuento, base imponible, cada impuesto desglosado, total de línea, total de pedido, moneda, lista de precios y promociones se calculan en backend/PostgreSQL con configuración autorizada.
- La API no acepta del frontend precios, tasas, bases fiscales, importes de impuestos ni descuentos calculados como autoridad.
- Los snapshots se generan dentro de la misma transacción que crea el pedido y son inmutables.
- Los cambios posteriores de productos, listas, impuestos o promociones no alteran los pedidos ya creados.
- El contexto organizacional, sucursal, entidad legal y actor se valida con las relaciones y permisos existentes.

## Interfaz
- Configuración administrativa integrada para listas de precios, asignaciones, precios por producto, reglas fiscales por producto y promociones.
- El formulario de producto permite asociar sus impuestos y escoger si el precio incluye o excluye impuestos.
- La vista POS muestra precio, descuentos, desglose fiscal y total final usando el resultado autoritativo del backend.
- No se muestran datos de demostración ni cálculos locales como fuente de verdad.

## Criterios de aceptación
- Migración ejecutable desde base vacía y desde el esquema vigente.
- Pruebas unitarias y PostgreSQL real para ámbitos, asignaciones, vigencias, precisión decimal, inclusive/exclusive, múltiples impuestos por producto, productos con tratamientos distintos, promociones, conflictos, aislamiento y concurrencia.
- Pruebas negativas para sucursal/entidad no relacionada, regla fiscal fuera de vigencia, reglas ambiguas, promoción no elegible, manipulación de importes desde cliente y modificación de snapshots.
- E2E desktop y móvil que configure listas/impuestos/promociones y cree pedidos reales verificando el desglose y total.
- Documentación de trazabilidad requisito → implementación → prueba → CI.
- No desplegar, fusionar ni declarar F2.3 cerrada hasta CI verde, revisión y aceptación funcional autorizada.

## Decisiones pendientes que no se deben inventar
- Precedencia/herencia corporación → entidad legal → sucursal (D0-10).
- Moneda funcional, monedas transaccionales, conversión y snapshot de tasa de cambio (D0-08).
- Jurisdicción fiscal, tipos/tasas legales, impuestos compuestos, exenciones y reglas de redondeo exigidas por cada jurisdicción.
- Política de acumulación, prioridad y exclusividad entre promociones.
- Reglas de elegibilidad y límites comerciales no especificados en los requisitos.
